what each of the four files answers, how to write one requirement, what a red/green task pair is,
and what the three lints check before a Builder sees the spec. They need two things from HARNESS:

Everything else — the EARS edge cases, the task-pair grammar the lint enforces, the four
citation forms, the namespace rule, the readiness grammar, the front-end contract paragraphs — is
exact text that agents and suites rely on and moves **verbatim** to the machine layer.

**Why HARNESS.md stays as a pointer page instead of disappearing.** Deleting it was considered and
rejected on three facts: (1) two suites pin a *human* sentence in it — the installed copy's
`[rationale and deletion ledger](RATIONALE.md)` link (`tests/test_install.sh:807`,
`tests/test_rationale_docs.sh:180`) — and a third appends to the installed file as a fixture
(`tests/test_init_drift_guard.sh:102`); a page that keeps that link keeps those rows green with no
edit, while deletion would re-point three suites to a counterpart for a sentence that is not a
contract; (2) C1 pairs each counterpart with a human doc of the same basename, and slice 1's
`index_problems` reports `no human counterpart docs/<NAME>.md` for a counterpart without one, so
`docs/agents/HARNESS.md` needs a `docs/HARNESS.md`; (3) slice 1's D3 already decided it. Moving the
whole file to `docs/agents/` and leaving no human doc was rejected for fact (2). What the pointer
page is: ≤20 lines, no `##` heading, no diagram — a definition, the counterpart link and three
onward links (CONCEPTS, WORKFLOW, RATIONALE).

also the one record of what 0.78.1 shipped. C1 declares `docs/history/` for exactly this. It moves
