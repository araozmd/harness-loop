# Fix — the installer copies Python bytecode (`__pycache__/`, `*.pyc`) into installs

## Problem / who
Every installed target, and the full test suite. `harness-install.sh`'s `copy()` runs a plain
`cp -R` from the source tree for each body directory, so the developer's local
`tools/__pycache__/*.pyc` lands in `.harness/tools/__pycache__/` of every install. That bytecode
is stale and machine-specific, and it may come from another Python version.

It also causes a flaky test. `tests/test_frontend_retirement.sh`, "mixed migration not
idempotent", fails only inside full-suite runs (23 isolated, parallel and runner runs all
passed). An instrumented full run showed the single differing file:
`.harness/tools/__pycache__/tasks-lock.cpython-313.pyc`. A concurrent suite runs
`tools/tasks-lock.py` against the shared source tree and rewrites that cache between the test's
two installs.

## Intended fix
- `copy()` in `harness-install.sh`: after `cp -R`, remove every `__pycache__/` directory and
  `*.pyc` file from the copied tree. Bytecode is a runtime artefact, never part of the body.
- New suite `tests/test_install_no_bytecode.sh`, written first and observed RED. It installs
  from an isolated source copy that holds `tools/__pycache__/x.cpython-313.pyc` and a stray
  `agents/y.pyc`, then asserts that neither ends up under `.harness/`, and that the install is
  otherwise unaffected (`tools/tasks-lock.py` is present).
- VERSION PATCH bump plus a CHANGELOG entry (🐛).

## How to verify
- `bash tests/test_install_no_bytecode.sh`, `bash tests/test_install.sh` and
  `bash tests/test_frontend_retirement.sh` all pass. `./init.sh` passes.
- The full suite no longer shows `test_frontend_retirement` failing.
