# Fix — doc-critic may write only its note; the Architect re-validates after the critic (GitHub issue #323)

## Problem / who
Spec authors and the human at the spec gate. Issue araozmd/harness-loop#323 (harness-feedback,
v0.107.0) reported that in an installed target the doc-critic, which is meant to be advisory
only, wrote a fabricated spec over one of the four files it was reviewing, and never wrote its
note. `tools/validate-board.py` and `init.sh` both exited 0 on that tree. The one check that
rejects the fabricated file (`tools/tasks-pair-check.py`, exit 2) runs before the critic in the
Architect's order, and nothing runs again afterwards. This is still true on main (v0.114.0):
- `agents/doc-critic.md:24-27` says "You return advisory findings; the generating agent applies
  fixes inline", but `:172` ("In addition to inline fixes, write…") and its "the issues found,
  each with the fix applied" bullet tell the critic to apply fixes itself. The file names no
  allowed write destination beyond "or a similarly scoped path".
- The `.claude/agents/doc-critic.md` shim grants `Write`. `tools/pi-dispatch.sh` grants write
  too, and neither confines it.
- `agents/architect.md` "Doc-critic checkpoint before spec-ready": nothing re-validates the four
  files after the critic returns, and a missing note is not treated as a failed checkpoint.

## Intended fix (structure over prose, per the ablation doctrine)
1. `agents/doc-critic.md`: one rule. The only file you may write is your note at
   `progress/<run>/doc-critic-<checkpoint>.md`. Never edit, create or overwrite any document you
   review or any other file. Remove the "inline fixes" / "fix applied" wording so findings are
   proposed fixes the caller applies. Keep the role text consistent everywhere it says advisory.
2. `agents/architect.md` checkpoint: before spawning the critic, record a checksum of each
   reviewed file. After it returns, recompute them. If any reviewed file changed, restore it
   (`git checkout -- <file>` when committed, otherwise from the Architect's own last write),
   record the incident in the progress note, and treat the checkpoint as failed. Then re-run
   `tasks-pair-check`, `plan-cite-check` and `readiness-check` after applying findings and before
   hand-off. A missing critic note counts as a failed or skipped checkpoint and is recorded, not
   silently passed.
   - Prefer a small helper over prose if it fits, e.g. `tools/critic-guard.sh snapshot|verify
     <files…>` (cksum based, exit 1 naming each changed file).
   - The same order applies wherever the doc-critic is spawned with documents it must not touch:
     check `/sdd-plan` and `/sdd-drill` and their emitters in `harness-install.sh`. Apply the
     guard there too if it is cheap; otherwise list them as out of scope in the PR body.
3. Do not change `validate-board.py` semantics (out of scope).
4. Regenerate glue with `sh harness-install.sh --self`; never hand-edit `.claude/`.
5. Tests:
   - a suite for the guard helper: an unchanged set exits 0; a changed file exits 1 and names it;
     a missing file exits 1;
   - prose pins on doc-critic.md (single write destination; no "fix applied"; a ban with a
     mutant);
   - prose pins on architect.md (snapshot before, verify after, lints re-run after, a missing
     note is a failed checkpoint).
   Each pin must fail without the fix.
6. If the helper is new and installed, register it wherever installed tools are listed, and add
   it to the installer's tool copy and its tests.
7. VERSION PATCH (or MINOR if a new installed tool ships; follow the repo's versioning policy) +
   CHANGELOG entry (🐛). Close issue #323 from the PR body with "Fixes #323".

## How to verify
- The new and touched suites are green (`tests/test_doc_critic*.sh`, `tests/test_architect*.sh`,
  `tests/test_install.sh` if a tool is added). `./init.sh` ok. A second `sh harness-install.sh
  --self` leaves the tree clean. `python3 tools/doc-cite-check.py` reports 0 findings.
- Run by hand: snapshot four files, change one, and verify exits 1 naming it.
